## 三、版本规划（0.4.1 起，不跨大版本）

### v0.4.1 — 建议范围（**只做 P0-2 + P2-1 + P2-2**）

| 项 | 内容 | 状态 |
|---|---|---|
| P0-2 | 启动时检测 `RealGuestMode` 配置与实际生效不一致，写进 progress.log | ✅ **9.578 完成** |
| P2-1 | 全核真 guest 挂机 ≥1 小时 | ⏭️ **operator 跳过** |

**为什么是这三个**：都低风险、都可回滚、都不改保护/隐藏路径。
P0-1（启动期控制）和 P1-1（`mem-bp dr`）都需要独立一轮且风险高，**不进 0.4.1**。

### v0.4.1 的实测结论

**P0-2** —— 三种场景（键不存在 / `=1` / `=0`）都验过，行为符合设计：

```
键不存在 : early-returns=12，无日志（默认开着）
=1       : early-returns=0，两行日志（含 raw=0x1）
=0       : early-returns=12，无日志
```

**P2-2** —— 真 guest 下 `mem-bench` 仍可用：

| 模式 | B 引擎中位数 | faster（A/B） |
|---|---|---|
| 桩 | 18,702,972 cycles | 2.16–2.47×（一个 5.12× 离群） |
| **真 guest** | **21,146,805 cycles** | **1.81–2.38×** |

**B 比 A 快 1.8–2.4×，且真 guest 下 B 比桩模式慢约 13%** ——
方向合理（B 走物理读，真 guest 下每次访问过 NPT 翻译）。

> **判据纪律**：A 的方差很大（44–89M），**比值不可靠**；要看 B 的绝对值。
> 另外 9.449 的 3.96× 与这里的 2.4× **不能直接对比** ——
> 目标进程（javaw 32MB vs explorer 6MB）、范围、页密度都不同。

## 四、判据纪律（这一节比清单本身重要）

盘点时发现的问题，几乎都是**判据失效**而非代码失效：

| 实例 | 判据怎么骗人的 |
|---|---|
| `invmrun=0x6` 被读成"停止信号太弱" | 它其实是"六个核的栈已不存在" |
| `early-returns=0` 被打印成"缺陷" | 桩模式下这是**正确读数** |
| `npt-view` 只认 `present=0` | 把 DECOY 的**成功隐藏**报成"没隐藏" |
| `mem-pte` 报 6/8 | 时序假象，不是缺陷 |
| 9.511 的"47 页从未被触及" | 观测窗口太短，**不是关于全部时间的断言** |
| 索引行数写 18 行 | 那条记录**根本没有正文** |
| 桩模式 11.6× 被当成全核代价 | 那是**桩自己空转**的开销 |

**所以每一条待办在开工前先回答两个问题**：

1. **我的判据能观察到这个事件吗？**（9.466 那条）
2. **如果这次读数变了，是代码变了还是判据变了？**

答不上来就先建观测，不要先改代码。
