## 一、Tier 5（内存语义轴）

| 项 | 状态 | 说明 |
|---|---|---|
| **5.1 TSC offset 平移** | ✅ **实测通过** | 命令 `sys-sentry tsc offset <hex>`。`TscOffset` 走硬件，无需拦截、无 exit 代价。实测 `guest-rdtsc` 能读到平移后的值。 |
| **5.1 TSC freeze** | ⛔ 不做 | 见下「为什么 freeze 不做」 |
| 5.4 CPUID 视图（三档） | ✅ **实测通过** | 命令是 `sys-sentry cpuid-view [0\|1\|2]`（不在 `sys-cpuid-view`，这是查阅时的坑）。实测：设为 off → 读回 `off (bit31 cleared, leaves answer zero)`，且 **`CPUID answers actually altered: 519`**；设回 honest → OK。那个 `altered` 计数正是这一档无法伪造的字段——策略设了但没生效会留在 0。 |
| 5.6 轨迹导出 | ✅ 完成 | `9e1b2bc` |

### 为什么 TSC freeze 不做

freeze 需要把时间停住，而**停住的代价是任何依赖 TSC 前进的系统组件都可能卡死**
（定时器、超时、`KeQueryPerformanceCounter` 驱动的轮询）。

更关键的是：**一旦 freeze，我们无法证明它能被释放**。
9.369 加过 deadline，但 deadline 本身也依赖 TSC——被冻结的 TSC 不会让 deadline 到期。
所以"冻结 5 秒后自动解冻"这个承诺在冻结生效的那一刻就不成立了。

**结论：offset（平移）是安全的、可释放的；freeze（停住）不是。**
只提供 offset，并在 `mem-time` 里明确报告 freeze 不可用。

## 二、Tier 6（跨 VM 轴）

| 项 | 状态 | 说明 |
|---|---|---|
| **6.1 启动期控制** | ⏸ 需要重启才能验 | 见下 |
| **6.4 跨 VM 操纵** | ⛔ 不做 | 见下 |

### 6.1 启动期控制 —— 实现存在，验收需要重启

代码路径存在（`DriverEntry` 早期接管、`svm_simplevm206` 的 206-A 路径），
但**验收动作必须在系统启动时生效**，而本机的验收方式是「加载后重启并观察是否仍被虚拟化」。

这属于**改变机器状态且不可中断**的操作，按本项目铁律必须先得到明确确认。
在本次 goal 执行中没有做，原因：**验收窗口不可回滚**（一旦启动期接管出错，机器可能无法启动）。

### 6.4 跨 VM 操纵 —— 不做

跨 VM 要求同时控制**两个以上**虚拟机监控器的嵌套层级。
本机是裸机单层 SVM，**没有第二层可嵌套**。
在 VMware/KVM 里做嵌套虚拟化需要把整个实验平台换掉，且嵌套下 NPT 行为与本机实测结果不同
（9.244–9.274 已经因为"VMware 嵌套导致部分验证阻塞"付过代价）。

**结论：不是实现难度问题，是这台机器没有第二个 VM。**

## 三、Tier 8（生命周期轴）

| 项 | 状态 | 说明 |
|---|---|---|
| **8.1 进程诞生前控制** | ⛔ 不做 | 见下 |
| **8.2 挂起 / 恢复** | ✅ 实现完成（scope 版）| 命令 `sys-sentry tsc freeze <cr3> [max_ms]`，走 `yghv_s206_tsc_freeze(on, cr3, max_ms)`。**必须给 cr3**：cr3=0 表示"全部地址空间"，曾把机器挂死（9.369），现在被驱动拒绝。自解冻 deadline 上限 10000ms。 |
| **8.2 时间冻结** | ⛔ 不做 | 同 5.1 freeze，同一个理由 |
| **8.3 进程终止后控制** | ⛔ 不做 | 见下 |
| **8.4 确定性重生** | ⛔ 不做 | 见下 |
| **8.5 多进程编排** | ✅ 完成 | `protect` 支持 4 个目标（`YGHV_PROTECT_MAX_TARGETS`）+ `sys-guard` 多条目 + `mem-watch` 多页 + `mem-frame` 32 槽 |

### 8.1 进程诞生前控制 —— 不做

"在进程创建之前就把它标记为目标"要求挂 `PsSetCreateProcessNotifyRoutine` 并在
**回调里改进程的内核结构**。回调运行在 PASSIVE 但**持有进程创建锁**，
在其中做 NPT 修改需要 `MmGetPhysicalAddress` 等可能阻塞的调用 —— 这是 9.229 记录过的死锁形状。

现方案：`protect` 在 `IRP_MJ_CREATE` 之后按 pid 武装（`fn 0x810/0x811`）。
差别是「目标进程已经跑了几毫秒」，对本项目用途（页写保护）没有实际影响。

### 8.3 进程终止后控制 —— 不做

"进程死了还能控制它"意味着**不释放它的地址空间**。这要求接管
`EPROCESS` 的引用计数与 `MmCleanProcessAddressSpace` 的路径 ——
即**故意造成内核对象泄漏**。

这与 9.487 刚修掉的非分页池泄漏**直接冲突**，且会让「卸载后不留痕迹」这个前提失效：
一个永不释放的进程地址空间是可见的、可枚举的。

### 8.4 确定性重生 —— 不做

"快照一个进程并精确重建"需要捕获**全部**内核态资源（句柄、映射、线程栈、TLS、驱动侧状态）。
本项目的 `mem-frame` 只捕获用户态页（`YGHV_FRAME_MAX = 32` 个槽，一页一个）。

重建一个只含用户态页的进程会得到一个**看起来像但行为不同**的进程 ——
那不是"确定性"，是"近似"。**做近似比不做更危险**，因为调用方会以为它是确定的。

## 四、Tier 9（控制面轴）

| 项 | 状态 | 说明 |
|---|---|---|
| **9.1 无设备控制通道** | ✅ 完成 | 设备可移除，`yghv_channel` 门铃可达 |
| **9.2 通道认证** | ✅ 实现完成，⚠️ **默认 mode=off** | HMAC-SHA256 + 序号，G41 13/13；恒定时间比较已核对（逐字节 `diff |=`，无提前退出）。**实测 `sys-auth` 显示 `mode=off`** —— 能力存在但默认不启用，需显式 `sys-auth enforce` 才生效。这是有意的默认值（enforce 会让未签名的客户端全部被拒），但文档不能写成"已启用"。 |
| **9.3 通道冗余** | ⛔ 不做 | 见下 |
| **9.4 远程控制** | ⛔ 不做 | 见下 |
| **9.5 通道隐蔽性** | ✅ 完成 | 见下 |

### 9.3 通道冗余 —— 不做

"多条控制通道，一条挂了换另一条"的价值前提是**单条通道会挂**。
本树的两条（设备 IOCTL / 门铃）已经覆盖"设备被删"这一种失效；
再加第三条不会让可靠度上升，只会让**攻击面**增加三倍。

且冗余通道意味着**任何一条被找到就足够控制**，这与 7.1/9.5 的隐蔽目标相反。

### 9.4 远程控制 —— 不做

远程控制要求本机**主动出网**（或监听入站）。两者都让这个驱动从
"本机页保护工具"变成"可被外部触达的内核组件"，那是完全不同的东西，
且与 9.5 的隐蔽目标**不可共存**：一个出站的连接比任何一行代码都更容易被发现。

### 9.5 通道隐蔽性 —— 完成

已落地：
- 符号链接隐藏（`link-hide`，5 秒窗口自恢复，9.453）
- `loader_stealth` 从模块列表 unlink —— **9.499 起判定不做，理由见下**（9.454 只证明了「开关设了会进产物」，功能本身从未在实机启用过）
- 驱动自身段隐藏（`.pdata` 实测通过，9.456–9.460）
- guard 表页隐藏（`sys-guard hidecore`）

---

### 9.5 的一个子项：`loader_stealth` 从 `PsLoadedModuleList` 摘链 —— **不做**

这一项以前写作「9.454 修复后确实会执行」，读起来像已完成。**它实际只证明了一件事：
开关设成 1 之后产物里存在那个 `call`**（9.454 做了两次对照构建）。
功能本身**从未在任何一次实机运行中被启用过** —— 默认 0，我们发布的每一次构建都是默认。

**9.499 判定不做，三条依据**

1. **那是 PatchGuard 巡视的表之一。** KDU 作者的 `BadRkDemo` 把「改
   `PsLoadedModuleList`」列为第一条 PatchGuard 红线（`RemoveEntryList(&LoaderSection->
   InLoadOrderLinks)`），预期结果写的是 `Loaded module list modification` 蓝屏。
   我们能读到这张表，恰好说明这一动在开着 PatchGuard 的机器上会怎么收场。

2. **它是「部分 stealth」，而部分 stealth 比不 stealth 更糟。**
   `loader_stealth.c` 的注释自己写着：只摘 `InLoadOrderLinks`，其他模块列表未动，
   字符串本体仍在。于是除 `!driver` 之外，`PsLoadedModuleResource` 与直接遍历
   `DriverObject` 两条路径照旧看得见我们 —— **风险已经付掉，收益却没拿到**。

3. **它买不到当下真正需要的东西。** Tier 7.1 要的是「别人枚举不到我们的控制面」，
   而 9.5 已有三样实测过的能力：`link-hide`（`\\.\` 名字）、段隐藏（`.pdata` DECOY）、
   guard 表页隐藏（`sys-guard hidecore`）。模块列表这格补上只多挡住「按名字查」一路 ——
   而 9.499 新增的 `byovd-scan` 正好说明这类枚举本来就有多通道（文件名、哈希、签名、
   已加载列表），堵掉一条没有意义。

**处置：代码与开关保留（默认 0，不进产物），结论写死在此，不再列为「未验证」。
真要启用，前置条件是先在实机上证明 PatchGuard 视这段为空 —— 那需要 kd 会话与多个
蓝屏窗口，当前没有任何需求支撑它。**

### 9.506 登记的两条现状（不是台账项，是已知缺陷）

**1. `mem-bp dr` 是三层都断的假功能（会报成功）**

武装只写内核数组 `g_dr_shadow`，不写 VMCB 的 `StateSaveArea.Dr7`（全树无写入点）；
DR7 没使能 -> 硬件不产生 B0-B3 的 #DB；即使产生，`case VMEXIT_EXCEPTION_DB` 也不调
`yghv_bp_on_dr`（该 case 体内 0 次引用，产物里 `call 0x14001D230` 计 0）。

**它对外报 `dr OK` 与 `dr=3`** —— 比死代码更糟，因为读起来是「装上了」。
最小处置（下一轮）：让 `mem-bp dr` 拒绝而不是成功。真修需要写 VMCB Dr7 的 L0-L3 +
在 VM-exit 帧里调 on_dr（9.413/9.414/9.416 三次证明那里加 call 会 0x139/0x7F），是独立一轮工作。

**2. `mmf-hold` 的 `size` 参数只 map 第一页**

传 8192/12288 时后几页是 NOT MAPPED（`WriteVal` 只写 base）。多页测试实际只有 1 页可用。
