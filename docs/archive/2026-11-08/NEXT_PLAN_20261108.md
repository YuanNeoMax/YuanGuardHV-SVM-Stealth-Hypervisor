## 二、可选方向（按价值排序）

### 方向 A：Tier 6.1 启动期控制验收 ⏸️

**台账里唯一剩下的「需重启」项。**

- 代码路径存在（`DriverEntry` 早期接管、206-A 路径）
- 验收动作必须在系统启动时生效
- **风险：启动期接管失败可能让机器不可启动**

**代价**：一次重启 + 可能进不了系统（需要用安全模式或恢复）。
**价值**：关闭台账最后一项。

**我的判断：风险高于收益。** 这台机器刚刚经历了 4 次蓝屏和一次 BIOS 引导异常，
再冒"可能开不了机"的风险，不合算。

---

### 方向 B：继续 RealGuestMode 的停止问题 🔴

**已知根因**：早退路径的终点是 `PsTerminateSystemThread`（在 guest 里），
`vmrun` 帧永久悬挂。

**已排除的解法**：
- DPC 扇出主动 vmmcall（9.550 验证：结构上缺 host 执行流）
- 在 `Sv206CoreThread` 尾部 tick（9.551 验证：时机错在启动阶段，停止标志未置位）

**剩下的唯一方向**：让 guest 在早退后 `jmp` 进 `Sv206GuestStub`，而不是走完 C 函数。

**为什么这个方向可能有希望**：
```
guest 完成 SvVirtualizeProcessor 的早退（C 帧展开 ✅）
  → 不 terminateFn
  → jmp Sv206GuestStub
  → 进入桩循环，开始 tick
  → 停止时握手可用（和桩模式一模一样）
```

**代价**：
- 需要在 guest 态从 C 代码跳到汇编桩
- 栈状态必须可控（`Sv206CoreThread` 的帧会留在栈上）
- **已产生 4 次蓝屏，这条路上再试风险明确**

**我的判断：技术上最有意思，但已验证过三次都不成立。**
如果要再试，必须先用一个**不加载驱动**的方式验证"从 C 跳到桩"这个动作本身可行。

### 方向 C：把这次的发现沉淀成可复用的检查 ⭐ 推荐

**本会话最大的收获不是修好了什么，而是发现了两类隐蔽缺陷：**

1. **"靠超时兜底"** —— 条件永远不满足，但因为有超时所以看起来能用
2. **"修了但没效果"** —— 这是找到真正原因的**唯一线索**

**可以做成什么**：

| 项 | 内容 |
|---|---|
| **审计其他等待循环** | 全树搜 `while (... && waited < N)`、`for (...spin...)`，检查每个条件是否**可满足** |
| **审计其他计数器语义** | 找出「谁写」「谁读」「单位是否一致」，就像 `invmrun` vs `CoresExited` 那样 |
| **加一个自检命令** | `sys-audit`：报告每个等待循环的条件、当前值、是否可满足 |

**价值**：本会话花了大量时间才发现 `active=12 vs 6核` 这一个错误。
**同类错误可能还有。**

**风险**：低（只读审计）。

## 三、我的建议

**先做方向 C（审计）+ 方向 D（收拢），不做 A 和 B。**

理由：

1. **A 的风险（开不了机）远大于收益（关闭台账一项）**。
   这台机器刚经历 4 次蓝屏 + BIOS 引导异常。

2. **B 已经失败三次**，每次失败都是蓝屏重启。要再试，必须先有
   "不加载驱动也能验证" 的办法，而那需要另一次架构改动。

3. **C 是唯一能防止同类问题再发生的方向。**
   `active=12 vs 6核` 这个错误潜伏了从 9.443 到现在，只因为它"慢但不崩"。
   **同类错误可能有第二个、第三个。**

4. **D 让这次的收获不丢失。** 本会话的文档很多，但没有一个入口。

```
1. 全树搜 while/for 循环里的超时模式

1. 列出所有 volatile LONG / LONG64 计数器
2. 每个标注：谁 ++、谁 --、谁读、单位是什么
3. 找出"跨文件读写但语义不一致"的
```
