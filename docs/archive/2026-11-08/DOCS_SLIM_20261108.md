## 二、每个动作的理由

### 2.1 `RESUME_PROMPT.md` 1420 → 692 行

**测量：第 8 节「剩余工作清单」占 747 行 = 全文 53%。**

而 `TIER_LEDGER.md` 已经把清单收敛成「8 完成 / 9 不做 / 1 需重启」。

**747 行在描述一个四行台账已经解决的积压。**

一个仪表盘已经给出答案时，再维护一份手工清单只会制造分歧。

**处置**：整节原文移入 `archive/RESUME_PROMPT_S8_WORKLIST_20260814.md`（一字未改），
主文档换成 12 行表格：**还开着的 1 项 + 3 件本会话新增的**。

### 2.2 7 份设计计划书移入 `archive/design/`

Tier 2/4/5/6/7/8-9 的**实施已结束**（台账：完成或不做的决定都已做出）。

设计文档此时的价值是「查设计意图」，不是「照着做」。**放在根目录会让人以为还在进行中。**

### 2.3 交接文档加索引，而不是删记录

**49 条记录是证据，不是垃圾。**

例如 9.513 记录了一次实测推翻了 9.464 的错误结论 ——
**那些读数是否定旧结论的唯一依据，删了就无法复核。**

**处置**：在开头加 49 行目录（标题 + 行数）。
新会话扫一眼找到要的那条，不必读 106 KB。

## 五、一个原则

**这次整理的方法：先测量，再动手。**

```
RESUME_PROMPT 1420 行 → 定位到第 8 节 747 行（53%）→ 发现它已被台账取代 → 归档
```

**没有"觉得太长了就砍"。** 每一处压缩都有一个可验证的理由：
- 被台账取代 → 归档
- 实施已结束 → 移到 design 归档
- 重复的地图 → 改成指向唯一入口
- 是证据 → **不删，加索引**

**"太多"和"太复杂"是两个问题**：前者靠归档解决，后者靠给结构。
