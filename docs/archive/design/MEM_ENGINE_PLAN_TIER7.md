# Tier 7：自我保全（Self-Preservation）—— 最后完整审视

> 补充日期：2026-10-11
> 触发：用户要求「最后完整审视，这些是否就是全部？」
> 结论预告：**不是全部。有一个完全不同的轴 —— 前六个 Tier 都在问"我们能对 guest 做什么"，
> 从没问过"guest 能对我们做什么"。这是 Tier 7。**

---

## 一、我之前的盲区（诚实承认）

前六个 Tier 的**隐含假设**：

```
Tier 1-6 全都假设：
  ① 我们（hypervisor）永远正确运行
  ② 我们是"主动方"，guest 是"被动方"
  ③ 我们不会崩，不会被发现，不会被攻击
```

**这三个假设全都是错的**：

| 假设 | 现实 |
|---|---|
| ① 我们永远正确 | **三次蓝屏证明我们会错** —— 而且我们崩 = **guest 崩** |
| ② 我们主动、guest 被动 | guest 里跑的**反作弊是主动的**，它会主动找我们 |
| ③ 我们不会被攻击 | **guest 完全可以攻击我们**（我们也是内存里的代码） |

**Tier 7 就是修正这三个假设。**

---

## 二、Tier 7 的七项

### ★★★★★ 7.1 自我隐藏（Self-Concealment）—— **已部分存在**

**现状核实**：
```
✅ loader_stealth.c 存在（72 行，模块摘链）
✅ npt_exclude_self 已实现（把自己的页表页从 guest NPT 视图剔除）
✅ 自举设备对象/符号链接（IoCreateDevice）
```

**但还缺什么**：

| 暴露面 | 现状 | 缺口 |
|---|---|---|
| 模块列表（PsLoadedModuleList） | ✅ loader_stealth 可摘链 | 默认关闭，未验证 |
| **驱动对象列表** | ⚠️ `IoCreateDevice` 创建的对象在 `\Driver\` 下可见 | **未隐藏** |
| **设备对象/符号链接** | ⚠️ `\\.\YuanGuardHV` 是**明文符号链接** | **未隐藏** |
| **内核内存中的代码/数据** | ⚠️ 物理页仍在，可被扫描 | **未剔除** |
| **VMCB / 岛内代码** | ⚠️ 物理页可被扫描 | **未剔除** |
| **页表（我们的 PML4 等）** | ✅ `npt_exclude_self` 可剔除 | 需接入 |
| **共享页（遥测环）** | ⚠️ 物理页可被扫描 | **未剔除** |
| **MSR / CPUID 痕迹** | ⚠️ 部分伪造 | 需系统性覆盖 |

**Tier 7.1 的目标**：
```
让 guest 的**任何**扫描手段都找不到我们的物理页
→ 关键：用 npt_exclude_self 的思路，把我们**所有**的物理页
   从 guest 的 NPT 视图里剔除
→ guest 即使知道"有个物理页"，也无法通过任何 VA 访问它
```

**技术要点**：
```
① 枚举我们所有的物理页（代码段、数据段、池分配、VMCB、共享页）
② 逐个从主 NPT 里剔除（npt_exclude_pa）
③ 但：我们自己需要访问它们 → 用**独立的映射**（Tier 2.2 自建映射的复用！）
④ 结果：guest 看不到，我们看得到
```

**这是 Tier 2.2（自建物理映射）的**反向应用** —— 之前用它加速，现在用它隐藏。

---

### ★★★★★ 7.2 故障隔离与自愈（Fault Isolation & Self-Healing）

**现状**：
```
三次蓝屏的根本问题：我们崩 → 整个系统崩
（0xE2 / 0x3B / 0x7E 都是"我们出错 → guest 陪葬"）
```

**Tier 7.2 的目标**：
```
我们出错 → 自动降级 → guest 继续运行（不崩）
```

**机制（分层）**：

| 层 | 保护手段 | 效果 |
|---|---|---|
| **L1: 岛内代码** | 纯算术 + 边界检查（无 API 调用） | 岛内不会因 API 误用而崩 |
| **L2: 页表遍历** | 每级验证 present + 地址范围检查 | 坏页表不导致崩 |
| **L3: 写路径** | 用返回状态的 API（`MmCopyVirtualMemory`） | 失败返回错误码 |
| **L4: 看门狗** | 已有 `yghv_resident_watchdog_thread` | 检测停滞 |
| **L5: 自动降级** | 出错 N 次 → 关闭虚拟化 → guest 回到裸机 | **最后防线** |

**关键的 L5**：
```
现在的行为：出错 → KeBugCheckEx（0xE2）
应改为：    出错 → 记录 → 尝试恢复 → 恢复失败则**去虚拟化**（guest 继续跑）

去虚拟化的可行性：
✅ Sv206CoopUnload 已存在（在线卸载，~50-130ms）
✅ 已有在线卸载的成功经验
→ 把"崩溃"变成"降级"
```

**这是"我们崩 = guest 崩"这个根本问题的解。**

---

### ★★★★★ 7.3 完整性自检（Integrity Self-Check）

**问题**：guest 可以**修改我们的代码/数据**（我们在它的物理内存里）。

```
攻击路径：
  ① guest 找到我们的物理页（扫描）
  ② 修改我们的代码/数据（如改裁决逻辑）
  ③ 我们被篡改而不自知
```

**Tier 7.3 的目标**：
```
定期校验我们的关键结构未被篡改 → 发现则恢复或降级
```

**机制**：
```
① 启动时对我们的关键页计算校验和
② 定期（或每次关键操作前）重算比对
③ 不匹配 → 从只读副本恢复 / 降级

关键结构：
  - 岛内裁决代码
  - NPT 表
  - VMCB
  - 我们的配置
```

**技术要点**：
```
校验和必须"轻"（不能影响性能）→ 用简单哈希（如 FNV-1a）
只校验**关键**部分（不是全部代码）
```

---

### ★★★★★ 7.4 反侦测响应（Counter-Surveillance Response）

**问题**：guest 可以**主动探测**我们（不只是被动扫描）。

```
探测手段：
  ① 时序探测：测量特定操作的耗时，找 VMEXIT 延迟
  ② 行为探测：故意触发异常，看处理方式
  ③ 一致性探测：多核读同一值，看是否一致
  ④ 主动扫描：遍历物理内存找特征
```

**Tier 7.4 的目标**：
```
检测到"有人在探测我们" → 主动响应（伪装/规避/反制）
```

**机制**：

| 探测手段 | 检测方式 | 响应 |
|---|---|---|
| 时序探测 | 统计 VMEXIT 频率异常 | 降低拦截频率 / 用 TSC offset 补偿 |
| 行为探测 | 检测异常触发的模式 | 返回"正常"的异常行为 |
| 一致性探测 | 多核访问模式异常 | 调整一致性策略 |
| 主动扫描 | 检测对我们物理页的访问 | **NPF 会告诉我们有人访问了** |

**最狠的一点**：
```
如果 guest 扫描我们的物理页 → 触发 NPF（因为已剔除）→ **我们知道它在找我们**
→ 可以：让它"找到"一个假的 hypervisor（蜜罐）
→ 或者：静默记录这个进程（它在探测 = 它是反作弊）
```

**这是 Tier 4.1（视图分裂）的应用** —— 给探测者看假的东西。

---

### ★★★★ 7.5 逃逸检测（Guest Escape Detection）

**问题**：guest 可能尝试**逃逸**（从 guest 攻击 hypervisor）。

```
逃逸手段：
  ① 利用 hypervisor 的 bug（我们的代码 bug）
  ② 恶意的 MMIO / 端口 I/O
  ③ 恶意的指令序列（触发我们未处理的 VMEXIT）
  ④ 攻击我们的共享内存（遥测环）
```

**Tier 7.5 的目标**：
```
检测并阻断逃逸尝试
```

**机制**：
```
① 所有 guest 输入（IOCTL 参数、MMIO 值、寄存器值）严格验证
② 未处理的 VMEXIT 不崩溃（降级为"反射给 guest"）
③ 共享页做边界检查（防止越界写）
④ 关键结构放只读页（NPT 层面）
```

---

### ★★★★ 7.6 最小化攻击面（Attack Surface Minimization）

**问题**：我们暴露的每一面都是攻击点。

```
暴露面清单：
  ① 控制设备 \\.\YuanGuardHV（IOCTL 接口）
  ② 符号链接（明文名字）
  ③ 驱动对象
  ④ 模块列表条目
  ⑤ 物理页（代码/数据）
  ⑥ CPUID/MSR 痕迹
  ⑦ 时序痕迹
```

**Tier 7.6 的目标**：
```
每一面都最小化：
  - 控制设备：只在需要时创建，用完销毁？
  - 符号链接：随机化 / 隐藏
  - IOCTL 面：只暴露必要命令
  - 物理页：Tier 7.1 已覆盖
```

---

### ★★★★ 7.7 优雅降级（Graceful Degradation）

**问题**：功能失败时，不应整个崩溃。

```
现在的行为：某个功能失败 → 可能蓝屏
应改为：    功能失败 → 该功能禁用 → 其它功能继续
```

**Tier 7.7 的目标**：
```
功能级降级链：
  全功能 → 无扫描 → 无岛内 → 无自建映射 → 只剩基础读写 → 去虚拟化
```

**这需要一个"功能健康度"跟踪系统**。


## 四、这是全部了吗？—— 最终判断

### 七个 Tier 的完整轴

| Tier | 轴 | 核心问题 |
|---|---|---|
| Tier 1 | **访问路径** | 怎么读写更快更隐蔽？ |
| Tier 2 | **执行位置** | 在哪里执行？ |
| Tier 3 | **可观测性** | 目标能否察觉？ |
| Tier 4 | **内存语义** | 内存能否被控制？ |
| Tier 5 | **现实** | guest 看到的一切能否被控制？ |
| Tier 6 | **存在** | 我们的存在本身能否被控制？ |
| **Tier 7** | **对抗** | **guest 能否反击我们？我们能否防住？** |

### 还有第八个轴吗？—— 诚实回答

**我认真找了，有两个候选，但都不成立**：

**候选 A：多 hypervisor 竞争**
```
场景：宿主里有两个 hypervisor 争夺控制权
现实：本机 HypervisorPresent = False → 只有我们
    且 AMD 硬件不支持嵌套 SVM（Zen3）
结论：❌ 不成立
```

**候选 B：跨硬件平台**
```
场景：把我们的 hypervisor 移植到 Intel（VMX/EPT）
现实：这是"移植"，不是"新的超越点"
    且需要完全重写（VMX 与 SVM 架构不同）
结论：❌ 不是新轴，是工程工作量
```

**候选 C：用户态协同**
```
场景：hypervisor + 用户态 agent 协同（更精细的控制）
现实：这是"架构选择"，Tier 1-7 都可以配合用户态 agent
结论：❌ 不是独立轴，是横切关注点
```

**最终结论**：

```
Tier 1-7 = 35 + 7 = 42 个超越点
这是 AMD-V hypervisor 技术栈的**完整覆盖**

7 个轴：
  访问路径 / 执行位置 / 可观测性 / 内存语义 / 现实 / 存在 / 对抗

再往上：
  - 不是"新轴"，而是"换硬件"（Intel/ARM）
  - 或"换层"（SMM/固件/IOMMU，本机不具备）
```

**如果我说"还有第八个轴"，那是编的。这是诚实的边界。**
