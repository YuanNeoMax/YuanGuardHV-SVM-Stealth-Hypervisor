# Tier 8 & 9：最后两个轴 + 穷尽性论证

> 补充日期：2026-10-11
> 触发：用户要求「最后完整审视，这些是否就是全部？」
> 结论：**不是。还有 2 个轴（Tier 8 / 9），并且我能给出"为什么到此为止"的严格论证。**

---

## 一、为什么之前漏了这两个轴

我审视了前 7 个 Tier 的**隐含假设**，发现它们全部建立在同一个前提上：

```
前 7 个 Tier 的隐含前提：
  guest 是"运行中的进程集合"，我们控制的是"它的内存/现实/存在"

从未问过：
  ① guest 的**生命周期**能否被我们控制？（不只是运行期）
  ② **谁来控制我们**？操作者与 hypervisor 之间的通道是什么？
```

**这两个问题对应 Tier 8 和 Tier 9。**

---

## 二、Tier 8：生命周期控制（Lifecycle Control）

### 核心命题

**前 7 个 Tier 都在 guest「运行期」做文章。Tier 8 控制的是「运行期之外」。**

```
guest 的完整生命周期：
  ① 创建前（进程还未存在）
  ② 创建中（进程初始化）
  ③ 运行期          ← Tier 1-7 全在这里
  ④ 挂起 / 恢复      ← Tier 8
  ⑤ 终止后（进程已死）
  ⑥ 重生（重启 / 重新加载）
```

### ★★★★★ 8.1 进程诞生前控制（Pre-Creation Control）

**是什么**：
```
现在：进程已经运行，我们才介入（set-target）
Tier 8：进程**创建的那一刻**就已经在我们的控制下
```

**机制**：
```
① 拦截进程创建（PsSetCreateProcessNotifyRoutine / 或在 hypervisor 层）
② 在进程**执行第一条指令前**完成：NPT 设置、目标注册、初始状态准备
③ 进程"从诞生起"就在我们的现实里
```

**为什么是"超越"**：

| 能力 | Tier 1-7 |
|---|---|
| 介入时机 | 进程运行中 |
| **进程无从对比"被控制前"的状态** | **不可能** —— 它没有"被控制前" |

**与 Tier 6.1 的区别**：
```
Tier 6.1：OS 启动前虚拟化（控制整个系统）
Tier 8.1：单个进程创建前介入（控制特定目标）
→ 粒度不同，互补
```

---

### ★★★★★ 8.2 挂起 / 恢复 / 时间冻结（Suspend / Resume / Time Freeze）

**是什么**：
```
现在：只能读写内存
Tier 8：可以让目标进程**完全冻结**（不执行任何指令），然后再恢复
       且冻结期间**外部观察者看不到异常**（不是"暂停"而是"时间停止"）
```

**机制**：
```
① 停止调度该进程的所有线程（不只是 SuspendThread）
② 冻结其时间视图（Tier 5.1 的 tsc_offset 精确控制）
③ 冻结期间：我们可以任意读写（无竞态）
④ 恢复：线程继续，**它感知不到时间的流逝**
```

**为什么是"超越"**：

| 能力 | 宿主内核 |
|---|---|
| SuspendThread | 能（但**可被检测**：线程状态可查、有挂起计数） |
| **完全无痕的冻结** | **不能** |
| **冻结期间目标无时间感知** | **不能**（RDTSC 仍在走） |

**用途**：
```
① 无竞态读写（冻结后读，不存在"读一半被改"）
② 检查点（冻结 → 快照 → 恢复）
③ 逆向分析（冻结在某条指令，反复观察）
```

---

### ★★★★★ 8.3 进程终止后控制（Post-Mortem Control）

**是什么**：
```
现在：进程退出 → 内存释放 → 我们失去控制
Tier 8：进程退出后，我们**仍然保有它的完整内存镜像**
```

**机制**（与 Tier 4.5 帧所有权接管相关但不同）：
```
① 检测到进程退出（进程回调 / NPF 观察到页表失效）
② 在系统回收物理帧**之前**，把目标的全部页**转移**到我们的保留区
③ 系统以为帧已释放（给它的"释放"路径看到干净的帧）
④ 我们保有完整镜像 → 可离线分析
```

**为什么是"超越"**：

| 能力 | 宿主内核 |
|---|---|
| 进程退出后读内存 | **不能**（已释放，可能被复用） |
| 崩溃转储（dump） | 能（但**需要预先启用**，且**可被检测**） |
| **透明的、目标不知情的完整镜像** | **不能** |

**用途**：
```
① 取证（进程退出后仍可分析）
② 密钥/凭据提取（很多程序退出前不清内存）
③ 行为分析（完整的历史状态）
```

---

### ★★★★★ 8.4 确定性重生（Deterministic Resurrection）

**是什么**：
```
Tier 6.2 是"整个 VM 快照/恢复"
Tier 8.4 是"单个进程的重生"：
  → 进程退出后，我们能把它**完整恢复**（内存 + 线程状态）
  → 它"死而复生"，且自己不知道
```

**机制**：
```
① 持续维护目标的完整状态镜像（内存 + 关键寄存器）
② 进程退出 → 我们在一个新的进程里重建它的状态
③ 外部观察者看到的是"进程重启了"（合理行为）
```

**为什么是"超越"**：

| 能力 | 宿主内核 |
|---|---|
| 重启进程 | 能（但**状态全丢**） |
| 进程检查点/恢复（CRIU 类） | 能（但**需要配合**，且**可被检测**） |
| **透明的、单方面的重生** | **不能** |

---

### ★★★★ 8.5 多进程编排（Multi-Process Orchestration）

**是什么**：
```
控制**一组相关进程**（如游戏主进程 + 反作弊进程 + 启动器）
→ 保持它们之间的一致性视图
→ 或者让它们看到互相矛盾的内容（视图分裂的跨进程版）
```

**用途**：
```
① 游戏 + 反作弊协同欺骗（两者看到不同的"事实"）
② 进程组的原子快照/恢复
```

## 三、Tier 9：控制权转移（Control Plane）

### 核心命题

**前 8 个 Tier 全都在说"hypervisor 能做什么"。Tier 9 问的是：谁在控制 hypervisor，以及这个通道本身是否可被观测。**

```
前 8 个 Tier 假设：操作者通过 IOCTL 控制我们
从未问过：
  ① 这个通道本身是否暴露？（\\.\YuanGuardHV 是明文符号链接）
  ② 操作者能否在"没有驱动接口"的情况下控制我们？
  ③ 控制通道能否对抗"驱动被卸载/被阻断"？
```

### ★★★★★ 9.1 无设备控制通道（Device-Free Control Channel）

**是什么**：
```
现在：\\.\YuanGuardHV 设备 + 符号链接（明文，可被发现）
Tier 9：**完全没有设备对象**，控制通过**共享内存 + CPUID** 之类的隐式通道
```

**现有基础（已核实）**：
```
✅ SSV1 CPUID leaf (0x41414142) 已实现（svm_simplevm206.cpp）
   → 这是"不需要设备就能通信"的雏形！
✅ 共享页机制（g_s206_addlog 等）
```

**机制**：
```
① 移除设备对象和符号链接（消除暴露面）
② 控制通过：guest 执行特定 CPUID → VMEXIT → 岛内读共享页 → 执行命令
③ 操作者只需一个用户态程序（不需要打开任何设备）
```

**为什么是"超越"**：

| 能力 | 现状 |
|---|---|
| 设备名可被发现 | ⚠️ `\\.\YuanGuardHV` 明文 |
| **无设备、无符号链接、无 IOCTL** | **不可能被"找设备"的手段发现** |
| **控制面完全不进入对象管理器** | 对象管理器里没有任何痕迹 |

**代价**：
```
⚠️ 失去标准 IOCTL 的便利（需自建协议）
⚠️ 用户态需要特权指令访问（CPUID 是用户态可执行的，合适）
```

---

### ★★★★★ 9.2 控制通道加密与认证（Control Channel Hardening）

**是什么**：
```
现在：任何管理员都能调用我们的 IOCTL（设备 ACL 保护）
Tier 9：控制命令**必须**经过认证，且通道加密
        → 即使有人拿到设备句柄，也无法控制我们
```

**机制**：
```
① 命令签名（只有持有密钥的操作者能下命令）
② 会话密钥协商（防重放）
③ 命令序列号（防重放攻击）
```

**为什么是"超越"**：
```
现状：设备 ACL 保护 = "谁能打开设备谁就能控制"
Tier 9：即使能打开设备，**没有密钥也不能控制**
```

---

### ★★★★ 9.3 控制通道冗余（Control Channel Redundancy）

**是什么**：
```
现在：设备被卸载 → 失去控制
Tier 9：多条控制通道（设备 + CPUID + 共享页 + ...）
        → 一条断了还有别的
```

**用途**：
```
① 对抗"驱动被卸载"（Tier 7.2 的降级链的补充）
② 对抗"设备被禁用"
```

---

### ★★★★ 9.4 远程控制能力（Remote Control）

**是什么**：
```
现在：本地 IOCTL（必须在本机执行命令）
Tier 9：控制可以来自**网络**（hypervisor 内嵌一个最小的网络栈）
```

**⚠️ 诚实评估**：
```
风险极高：
  ① 网络栈代码量大（攻击面爆炸）
  ② 违反 Tier 7.6（最小化攻击面）
  ③ 本机无 IOMMU，网络设备 DMA 无法拦截
结论：⚠️ **不建议做**。作为设计存档，但明确标注"与 Tier 7 冲突"。
```

---

### ★★★★ 9.5 控制通道的隐蔽性（Channel Stealth）

**是什么**：
```
控制行为本身不留下痕迹：
  ① 不下发 IOCTL（用 CPUID/共享页）
  ② 不创建文件/注册表项
  ③ 不产生 ETW 事件
  ④ 命令执行**在岛内完成**（Tier 2.1）
```

## 四、穷尽性论证（为什么到此为止）

### 4.1 方法论：用"控制对象的维度"做穷尽

我不是随意列举，而是**穷举 hypervisor 能控制的"维度"**：

```
一个 hypervisor 站在 GPA→SPA 翻译点上，它能控制：

维度 1  内存的内容与语义        → Tier 4（视图分裂、时间维度、别名）
维度 2  内存的访问路径          → Tier 1（零 API、页表遍历）
维度 3  代码的执行位置          → Tier 2（岛内、自建映射）
维度 4  访问的可观测性          → Tier 3（A/D 位不变、隐身读取）
维度 5  guest 的观测面          → Tier 5（时间、指令、系统调用、硬件、I/O）
维度 6  guest 的存在时间        → Tier 6（启动前、快照、重放）
维度 7  对抗关系（攻防）        → Tier 7（自我隐藏、故障隔离、反侦测）
维度 8  guest 的生命周期        → Tier 8（诞生前、冻结、死后、重生）
维度 9  控制通道本身            → Tier 9（无设备、认证、冗余）
```

**这 9 个维度是否穷尽？**

### 4.2 穷尽性证明（反证法）

**假设存在第 10 个维度**。那么它必须满足：
```
① 它能被 hypervisor 控制（在 VMRUN 边界内可干预）
② 它不属于上述 9 个维度中的任何一个
```

**逐一检验 hypervisor 能干预的一切**：

| hypervisor 能干预的对象 | 归属维度 |
|---|---|
| GPA→SPA 映射 | 维度 1 |
| NPT 权限位 | 维度 1 |
| VMCB 的 ControlArea（拦截位、nCR3、tsc_offset） | 维度 5 |
| VMCB 的 StateSaveArea（寄存器、RIP） | 维度 5 |
| 事件注入（vintr / event_injection） | 维度 5 |
| 执行时机（何时 VMRUN/VMSAVE） | 维度 3 |
| 自身的代码/数据 | 维度 7 |
| 自身的生命周期 | 维度 7 |
| guest 的进程生命周期 | 维度 8 |
| 控制接口 | 维度 9 |
| 内存内容 | 维度 1 |
| 访问时序 | 维度 5 |
| 中断/异常 | 维度 5 |
| I/O 与 MMIO | 维度 5 |
| 多核一致性 | 维度 5 |
| **设备 DMA** | ⚠️ **无 IOMMU 时无法干预** |
| **物理硬件（温度、功耗、真实时钟）** | ⚠️ **无法干预** |

**结论**：**所有可干预对象都落在 9 个维度内。** 反证成立，**不存在第 10 个维度**。

### 4.3 两个"不可干预"的边界（诚实标注）

| 边界 | 原因 | 本机 |
|---|---|---|
| **设备 DMA** | 需要 IOMMU (AMD-Vi) 才能拦截 | ❌ **ACPI 未暴露** |
| **物理层**（温度/功耗/真实时钟） | 需要 BMC/SMM | ❌ 超出范围 |

**这两个不是"还没想到的超越点"，而是"硬件不支持的边界"。**

## 八、最终回答

**问题**：「这些是否就是全部？」

**答案**：
```
不是。还有 2 个轴（Tier 8 生命周期 / Tier 9 控制通道），
并且我给出了**穷尽性证明** —— 用"hypervisor 能干预的一切对象"做反证，
所有可干预对象都落在 9 个维度内，不存在第 10 个维度。

两个不可干预的边界（诚实标注）：
  ① 设备 DMA —— 需要 IOMMU，本机 ACPI 未暴露
  ② 物理层（温度/功耗/真实时钟）—— 需要 BMC/SMM，超出范围

这两个不是"没想到"，而是"硬件不支持"。
```

**52 项超越点 = AMD-V hypervisor 技术栈的完整覆盖。**

**如果还有第 10 个维度，那一定是我论证有漏洞 —— 但目前我找不到。**
