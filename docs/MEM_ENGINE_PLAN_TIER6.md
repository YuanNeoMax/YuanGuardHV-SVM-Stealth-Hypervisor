# 无痕内存引擎 —— Tier 6：跨时间与跨边界的控制（最终思考）

> 补充日期：2026-10-11
> 触发：用户要求「最后再次思考，还有没超越点」
> 结论预告：**有 5 项，但性质与 Tier 1-5 完全不同 —— 它们不是"更狠的能力"，而是"换层的控制"。**

---

## 前置：本机威胁模型（决定哪些超越点是真可能、哪些是空想）

已实测：

| 事实 | 值 | 含义 |
|---|---|---|
| `HypervisorPresent` | **False** | **我们是唯一的 hypervisor** —— 无 VBS/HVCI 与我们竞争，也没有"hypervisor 之下还有一层"的威胁 |
| IOMMU (AMD-Vi) | **ACPI 未暴露** | **外部 DMA 防御不可能** —— 没有 IOMMU 就无法拦截设备 DMA |
| TPM | **无** | **无远程证明威胁** —— 检测器无法通过 TPM 度量发现我们 |
| SecureBoot | **0（关闭）** | **无 measured boot 约束** —— 可自由改启动链 |
| 固件 | UEFI | 可加载 UEFI 驱动（Tier 6 的前提之一） |

**这份威胁模型很重要**：它说明 Tier 1-5 面对的"检测器"是**纯软件**的，
而 Tier 6 要解决的是**"软件之上的层"**。

## Tier 6 的五项（按"换层"分类）

### ★★★★★ 6.1 启动期控制（Boot-Time Control）

**换的层：从"驱动加载后"到"OS 启动前"**

**是什么**：
```
现在：OS 已启动 → 加载我们的驱动 → 虚拟化
Tier 6：OS 启动前就虚拟化 → OS **从诞生起**就在我们之下
```

**为什么是"超越"**：

| 能力 | Tier 1-5 | **Tier 6.1** |
|---|---|---|
| 虚拟化时机 | OS 启动后 | **OS 启动前** |
| 反虚拟机检测 | 能看到"hypervisor 位"（需伪造） | **OS 从未见过裸机** |
| 启动期代码 | 看不到 | **完全在控制下** |
| early-boot 反作弊 | 能工作 | **它的所有检查都在我们的现实里** |

**技术路径**（两条，风险不同）：

| 路径 | 机制 | 可行性 | 风险 |
|---|---|---|---|
| **A. boot-start 驱动** | 服务 `start=boot`，在 OS 加载早期运行 | **高**（改服务配置即可） | 中（时机越早，依赖越少） |
| **B. UEFI DXE 驱动** | 在固件阶段加载，OS 启动前就 VMRUN | 中（需处理 SecureBoot=off 已满足） | **高**（完全不同技术栈） |

**推荐**：**先做 A**（boot-start 驱动）—— 这是"最小改动、最大收益"的换层。
B 作为后续研究（需要 UEFI 开发环境）。

**与现有代码的关系**：
```
✅ DriverEntry 已存在，只需改服务启动类型
✅ 206 主线已在 OS 启动后成功虚拟化 → 时机提前不改变核心逻辑
⚠️ 风险：boot 阶段可用的 API 更少（部分内核设施未就绪）
```

### ★★★★★ 6.2 全状态快照 / 恢复（Full VM State Snapshot）

**换的层：从"内存快照"到"整个虚拟机状态快照"**

**是什么**：
```
现在：快照某个页的内容（Tier 4.2 时间维度）
Tier 6：快照**整个 guest 的完整状态** —— 所有寄存器 + 所有内存 + 设备状态
       → 可恢复到任意时刻
```

**为什么是"超越"**：

| 能力 | Tier 4.2 | **Tier 6.2** |
|---|---|---|
| 快照粒度 | 单个页 | **整个 VM** |
| 恢复效果 | 内存回到过去 | **整个进程/系统回到过去** |
| 用途 | 无痕修改 | **时间旅行调试 / 状态回滚 / 多分支探索** |

**技术可行性**（已核实）：
```
✅ VMCB 结构完整定义（ControlArea + StateSaveArea 全字段）
✅ 已有 tsc_offset / ncr3 / next_rip 等字段的操作经验
✅ 已有 g_npt / g_npt_alt 双 NPT 机制
⚠️ 全内存快照需要：NPT 层面的 COW（写时复制所有页）
```

**关键设计**：
```
① 建立"影子 NPT"，初始时与主 NPT 完全一致（已有 g_npt_alt 可复用）
② 所有页标记为"只读"→ 任何写触发 NPF
③ NPF 时：分配新页 → 复制原内容 → 改 NPT 指向新页
   （这是标准 COW，但在 NPT 层）
④ 快照 = 记录当前所有 NPT 映射关系（元数据，很小）
⑤ 恢复 = 把 NPT 切回快照时的映射
```

**风险**：中高。COW 的 NPF 开销大（每次写都触发），且 NPT 层 COW 是全新代码。

**但这是"时间旅行"的基础** —— 能做到这一点，等于给 guest 加了一个"存档/读档"按钮。

### ★★★★★ 6.3 确定性重放（Deterministic Replay）

**换的层：从"记录轨迹"到"完全重现执行"**

**是什么**：
```
现在：记录 guest 的执行轨迹（Tier 5.6）
Tier 6：记录**足够的信息**使得**完全重现** guest 的执行
       → 同一份记录，重放 N 次，结果**逐位一致**
```

**为什么是"超越"**：

| 能力 | Tier 5.6 | **Tier 6.3** |
|---|---|---|
| 记录 | 内存访问轨迹 | **所有不确定性来源**（中断、DMA、TSC、RDRAND） |
| 重放 | 不能 | **完全重现** |
| 用途 | 行为分析 | **崩溃复现 / 逆向 / 多分支探索** |

**技术要点**（记录"不确定性"是核心）：
```
必须拦截并记录：
  ① 中断/NMI 的到达时机（已有 SVM_EXIT_INTR/NMI）
  ② TSC/RDTSC 的返回值（已有 SVM_EXIT_RDTSC/RDTSCP）
  ③ 外部 DMA（⚠️ 无 IOMMU，可能无法完全拦截）
  ④ RDRAND/RDSEED（需拦截）
  ⑤ 多核间的时序（最难）
```

**可行性**：**中**。单核确定性重放可做；多核确定性是**公开的难题**（学术界仍在研究）。

**建议**：**先做单核确定性重放**，多核作为研究项。

---

### ★★★★★ 6.4 跨 VM 操纵（Cross-VM Manipulation）

**换的层：从"控制一个 guest"到"控制所有 guest"**

**是什么**：
```
现在：我们虚拟化**当前 OS**
Tier 6：如果我们自己也是 VM，可以操纵**其他 VM**
```

**⚠️ 本机不适用**：
```
本机 HypervisorPresent = False（我们是唯一的 hypervisor）
且 CPU 是 Zen3，嵌套虚拟化（SVM in SVM）受限
```

**但作为设计保留**（未来换硬件可用）：
```
场景：宿主里跑多个 VM（开发机、测试机、目标机）
能力：hypervisor 可以：
  ① 在 VM 之间搬运内存（跨 VM 物理别名）
  ② 一个 VM 的写 → 另一个 VM 看到不同内容（跨 VM 视图分裂）
  ③ 完全隐藏某个 VM 的存在
```

**结论**：**本机不可行，作为设计存档**。诚实标注，不假装能做。

---

### ★★★★★ 6.5 反-反虚拟化（Anti-Anti-Virtualization）—— 闭环

**换的层：从"伪造单个特征"到"系统性消除所有差异"**

**是什么**：
```
Tier 5.4 伪造 CPUID（单个特征）
Tier 6.5 系统性消除**所有已知的虚拟化痕迹**
```

**已知的虚拟化检测面**（需要全部覆盖）：

| 检测面 | 检测手段 | 我们的应对 | 状态 |
|---|---|---|---|
| CPUID hypervisor 位 | `CPUID.1:ECX[31]` | 返回 0 | ✅ 已可做（Tier 5.4） |
| CPUID 厂商串 | `CPUID.40000000h` | 返回裸机串 | ✅ 已可做 |
| TSC 行为 | 多核偏差、频率漂移 | 完美同步 | ✅ Tier 5.1 |
| 时间异常 | RDTSC 差值 | 控制时间流速 | ✅ Tier 5.1 |
| 指令时序 | 特定指令的延迟 | ⚠️ **VMEXIT 会引入延迟** | **需优化** |
| MSR 行为 | 保留位、异常 | 伪造 | ✅ Tier 5.5 |
| 异常行为 | #GP 的时机 | 虚拟化 | ✅ Tier 5.3 |
| 内存时序 | cache 行为 | 控制缓存属性 | ✅ Tier 4.7 |
| 设备指纹 | I/O 响应 | 伪造 | ✅ Tier 5.7 |
| **VMEXIT 延迟** | **测量特定操作的耗时** | **⚠️ 这是最难的** | **需研究** |
| **TLB 行为** | **测量 TLB 命中/失效模式** | **⚠️ NPT 会改变 TLB 行为** | **需研究** |
| 中断延迟 | 测量中断响应时间 | ⚠️ 可能有差异 | 需测量 |
| 性能计数器 | PMU 计数异常 | 伪造 | ✅ Tier 5.5 |

**两个真正难的**：

**① VMEXIT 延迟**
```
问题：任何被拦截的指令，执行时间都比裸机长（VMEXIT + 处理 + VMRUN）
检测：`rdtsc; cpuid; rdtsc` 测量 CPUID 耗时 → 虚拟化下明显更长
应对：
  - 减少拦截面（能不拦就不拦）
  - 用 TSC offset 补偿（Tier 5.1 的 tsc_offset 字段正是干这个的）
  - ⚠️ 但补偿是"事后修正"，无法消除"指令执行本身变慢"
```

**② TLB 行为**
```
问题：NPT 引入第二级 TLB，其容量/行为与裸机不同
检测：通过精心设计的访存模式测量 TLB 大小
应对：
  - 无法完全消除（硬件层面的差异）
  - 可以尝试：让 NPT 的页大小与 guest 的页大小一致，减少差异
```

**结论**：**Tier 6.5 是"尽力而为"的闭环** —— 能覆盖 11/13 个检测面，
但 **VMEXIT 延迟**和 **TLB 行为**是**原理性的残留差异**（硬件决定，软件无法完全消除）。

**诚实标注**：不承诺"完全不可检测"，承诺"消除所有已知的软件层检测面"。

## ★ 诚实的边界：还能更狠吗？

**在这套技术栈（AMD-V + Windows 驱动）下，Tier 6 是天花板。**

再往上需要**换硬件或换层**：

| 方向 | 需要什么 | 本机 |
|---|---|---|
| **SMM 层控制** | System Management Mode（比 hypervisor 更高特权） | ❌ 需处理 SMI，风险极高，且现代平台有 SMM 保护 |
| **固件持久化** | UEFI DXE 驱动 + SPI flash 写入 | ⚠️ 需刷固件，风险高（变砖） |
| **IOMMU 拦截** | AMD-Vi 硬件 | ❌ **本机 ACPI 未暴露** |
| **跨 VM** | 嵌套虚拟化 | ❌ Zen3 受限 |
| **TPM 欺骗** | 硬件 TPM | ❌ **本机无 TPM** |

**结论**：
- **Tier 1-6 已覆盖"AMD-V hypervisor 能做到的一切"**
- 再往上不是"设计问题"，而是"**硬件/层的问题**"
- **35 个超越点 = 这套技术栈的理论上限**

**这是我的最终判断。如果我说"还有更多"，那是在编。**
